报告对象：用 75 只狐狸及其口衔方块，在 Minecraft 基岩版／网易版中实现的第一人称 AK47 FMBE 枪械。整理日期：2026-10-10。读者：继续维护、研究或重新实现该项目的 AI。

这是历史复盘、当前源码说明和接手资料，不是新补丁。本文没有在游戏中运行新命令，也没有重新验证所有历史实验。实际世界基线来自《AK47_命令提取.txt》：109 个世界命令方块，另有结构模板命令。常态／跑动／机瞄和开火有用户成功反馈；C23 换弹命令包属于已生成但未在本轮可见证据中确认实机成功的候选实现。

证据标签：

- [U] 用户在游戏中的明确反馈。证明其当次条件下的现象，不自动推广到其他版本、设备或生命周期。

- [C] 本轮读取的命令、模型、动画源码可以直接证明的事实。

- [D] 官方文档或原版动画定义给出的接口／变换语义。原版样例版本不等于用户运行版本。

- [A] 由上述事实推导的数学或工程解释。

- [H] 尚未由排他实验确认的机制假设。

- [x] 缺少证据，不能下结论。

优先级不是简单按文件日期排序，而是：用户后续明确实测 + 对应最终源码 > 同期可复现记录 > 早期交接的“当前结论” > AI 的猜测。2026-10-05 的某些文件仍写“未修复”，那是阶段性状态，不能据此否认后来的稳定结果。

本文保留成功代码和失败记录，但失败代码不属于安装步骤。附录中的世界清理命令也只是原存档事实，不授权接手 AI 在其他世界直接执行。不得把“离线检查通过”“命令接受”“动画表达式有反应”“实机稳定”混为同一种验证。

可见聊天记录主要保留用户消息及少数引用的其他 AI 报告。许多“正常”“恢复了”没有对应的完整助手命令。对此只能按已保存源码及交接记录重建阶段，不能为每句短反馈虚构一个确切修订号。

## 01 最终成果与仍然未知的边界

已达到的目标：

1. [U/C] 75 个口衔方块组合成 AK47 外形，支持非等比缩放、各部件独立几何姿态及整枪跟随视角。

2. [U] 经根骨骼运输与最终帧内补偿调整，早期的零件分离重组得到明显改善，后期整枪弹簧式抖动降至用户评价“和静态效果几乎一致”。

3. [U/C] 常态、跑动、机瞄可以切换；采用单一姿态计算器和一次性状态信号，解决旧方案相互叠加。

4. [U/C] 跑动横摆约 75°，调整枪械靠近玩家；用户最终反馈“完美，动画已经全部实现”。该反馈指当时的持枪／跑动／机瞄，不等于后来换弹也已实测。

5. [U/C] 投掷雪球触发开火，利用 9 层 c=2 命令分支驱动射线步进，不依赖额外的专用射线实体。

6. [C] 已加入命中伤害、粒子、旋转型屏幕抖动、僵尸破门音效及停止狐狸／雪球音效的命令。

7. [C] 召唤建档与渲染安装分离；狐狸堆叠在玩家附近后仍可依靠持久标签重建零件身份。

没有被证明已经解决：

- [U/X] 大幅转动视角时短暂消失曾持续存在。不能把最终“小幅抖动接近静态”扩写成“任意转动永不消失”。

- [U/X] 隐藏原生手持物品的早期方案无效。把狐狸移到高处是模型显示管理的一种现有处理，不等于隐藏玩家原生手持雪球。

- [x] 不同准确游戏版本、不同帧率、低帧率、暂停、切维度、卸载重载、第三人称、多人、多相机的完整兼容性。

- [x] C23 换弹实机效果、换弹与弹药扣除／补充／禁止开火的整合。

- [x] 相机查询、实体位置查询、实体绘制插值和各动画骨骼应用在用户引擎中的完整内部时序。

- [x] 原生动画缓存到底位于实体、控制器、客户端哪个层级。退出世界或重召狐狸的观察不足以单独确定其实现。

- [x] “世界首创”“超越所有 FMBE 作品”等范围性评价，没有覆盖全部同类作品的调查支撑。

## 02 需求、环境与交付约束

本项目的目标环境是基岩版／网易版纯命令世界。允许命令方块、原版动画、Molang、标签和记分板；离线生成脚本及 HTML 预览是开发工具，不属于游戏运行时依赖。不要擅自改成资源包、行为包、脚本 API、插件或 /function 工程。

用户明确是单人游戏，不要求租赁服级、多用户隔离、工业化部署或复杂辅助实体管理。工程抽象必须服务当前玩法，不能把简单状态按钮改成一套未经要求的系统。

约束随时间变化：

- 早期用户不愿重装，重建成本高，应优先最小修改与逐字回退。

- 后期用户明确表示重召狐狸已经方便，允许按原来的安装方式重建；不能把早期限制当永久禁令。

- 原始“尽量少的常驻命令块”是阶段目标。最终世界实际有 8 个循环块，不能声称整套成品严格只有 5 个常驻块。

- 用户希望给出可直接复制的整条命令和明确修改位置，不能要求他自行在万字表达式里找几个字符。

- 用户希望召唤与渲染分区，曾要求两个 JSON 合为一个文件，通过分区组织即可。

- 命令复制助手格式使用数字 "mccmd": 1；错误字符串 "r1" 已经造成“不支持的格式版本”交付事故。以后导出必须读取相应技能并按实际模式校验。

- 中文标签是当前世界真实使用方式，不必全部替换成英文。

- 历史资料要求自定义标识避免某些敏感字符组合，如 av、sb、sz、nc，优先保守命名。应检查自定义名字及表达式兼容性，不应改坏原版动画标识。源码中的若干常量写成除法表达式，未经完整验证不要擅自美化合并。

- 原始 JSON、HTML 和命令块格式不是彼此可直接替换的格式；包格式正确也不代表动画正确。

准确游戏版本号没有在本轮证据中得到确认。不得仅根据原版样例 format_version 或文件生成日期推断用户正在运行哪一版网易客户端。

## 04 架构与三种时间尺度

服务器／命令侧：

- 生成 75 只成年狐狸、发放方块、加药水、建立身份标签。

- 每游戏 tick 跟随传送狐狸到玩家眼前。

- 检测持枪、移动、潜行及跳跃，产生一次性姿态标签。

- 发出一次 playanimation 安装／状态信号。

- 使用雪球触发并在一次命令链中完成射线步进和伤害。

客户端／Molang 侧：

- 每只狐狸有自己的变量状态。

- 从标签对应的分组动画赋值重建编号。

- 持续查零件表，计算姿态权重、相机基底、矩阵和骨骼变量。

- 使用原版动画将变量应用到 root、body、head 等骨骼。

- 采样位置变化与 q.frame_alpha，补偿跟随传送的帧内误差。

开发／离线侧：

- HTML 展示几何与动作意图。

- 生成或检查长命令、JSON、矩阵、零件映射及回退一致性。

- 无法代替客户端动画实际安装、剔除、插值和骨骼叠加的验证。

必须分清：

1. 一次性安装命令的执行时间；

2. 服务器 tick 的跟随与检测时间；

3. 客户端每帧求值与绘制时间。\
   把渲染安装链设成循环，只会反复发送安装命令，不能自动修复第 3 层的时序与剔除问题。持续动画可以由一次 playanimation 安装后持续求值，不等于每帧都要服务器重发命令。

## 05 75 实体模型的表达能力与成本

[C] 一个模型零件对应一只狐狸口中的一个方块。隐藏狐狸本体，保留可见口衔物，借用原版骨骼动画变换它。部件不是任意三角网格，而是立方体经过缩放、单轴拉伸／压缩、旋转和平移形成的几何体。

完整模型分组：

- 机匣 12；

- 枪托 7；

- 握把与护圈 9；

- 弹匣 24；

- 护木 6；

- 枪管与导气管 8；

- 瞄具 9。\
  合计 75。方块材质为黑色混凝土 40、灰色混凝土 28、金合欢木板 7。

本轮把 HTML 的 75 个中心点，与最终 R001 查表位置减去固定偏移 (0.66, -0.174, 0.245) 后逐一匹配：

- 75 项一一对应，无重复和缺失；

- 最大中心差约 1.68×10^-16 格，属于浮点舍入量级；

- 材质与召唤链实际选择器完全一致；

- 69 项具有非等比缩放，6 项等比；

- 单轴尺寸由 k12×k13² 重建，与模型中不同于另两轴的尺寸最大差约 1.38×10^-13。

因此“75 只说明没有拉伸”是不成立的。实体数量主要花在多段曲线、不同材质、弹匣侧棱、握把、枪托、瞄具等相互独立的可见细节上。一个长条可以一实体完成，但无法用同一个普通口衔方块同时表达分离零件、不同颜色和一条带细棱的弯曲弹匣。

k13 是对应单轴比例的平方根参数，不是直接的最终长宽比。存在小于 1 的压缩值，不能把所有非等比操作都称为“沿最长轴增长”。

性能成本包含 75 个原生实体、多个持续动画状态、每实体每帧的查表／矩阵／三角运算、每 tick 跟随，以及开火时的命令分支。没有本轮设备帧率基准，不能承诺固定 FPS。若要减实体，优先减少弹匣棱线或合并同材质共线细节，并重建编号映射；不要误认为删掉缩放就能保持同样外形。

## 06 狐狸生成、编号与标签的真正用途

[C] 生成栅格：\
position(a,b,c) = (0.5+2a, 100+2c, 0.5+2b)\
a,b ∈ {0,1,2,3,4}，c ∈ {0,1,2}\
id = a + 5b + 25c，id ∈ [0,74]。

通过按现有实体批量复制召唤构造 5×5×3，而不是手写 75 个 summon。这依赖每一步的选择范围和顺序；把全部复制改成不加限制的循环会指数增长。

身份标签共有 13 类坐标标签：\
k47x0..4、k47z0..4、k47y0..2。\
每只狐狸持有其中 3 个，再加总组标签 k47f；名称也为 k47f。渲染安装时不同选择器写：\
k41=a，k42=b，k43=c；\
R001 每帧重建 k44=k41+5*k42+25*k43。

标签的作用是持久身份，不是每帧传坐标。所有狐狸 tp 到同一点后，q.position 仍能返回它们当前坐标，但不能从相同坐标推回各自是哪一个部件。保存原始格点身份后，才能堆叠着重新安装渲染。

可以不用这些标签，但要接受别的身份保存条件：

- 在栅格上先由 q.position 计算编号，随后只依赖本次会话内的变量；

- 或重进世界后重新排列／重建；

- 或使用其他可查询的持久身份方案。\
  标签不是 FMBE 数学前置的必需项，是“堆叠后可初始化”和“重进后不重新排列”这两个需求的实现选择。

退出重进后仍可能需要按一次渲染初始化，这与标签有用不矛盾：标签保存部件是谁；客户端动画及 Molang 变量需要重建的是部件如何显示。不要把持久实体标签和客户端临时变量当成同一寿命。

材质编号不是简单按 0..39 全黑、40..67 全灰、68..74 全木：

- 黑：0..19、25..44，共 40；

- 木：50..56，共 7；

- 灰：20..24、45..49、57..74，共 28。\
  HTML 原始数组序号也不是最终狐狸 id。模型附录给出经过核对的一一映射；换弹和材质修改必须使用这个映射。

## 07 召唤与渲染分离，以及加载／可见性问题

[U] 最早表现为大量隐身狐狸叼着未组合方块。把渲染链改循环也无效。用户把狐狸固定在空中、使其进入视野，再执行渲染，随后启动跟随，能够成形。后来发现根位置不在视野内时，已被大幅骨骼平移到屏幕前的方块也可能消失。

必须区分三个状态：

- 命令选择器能选到实体；

- 客户端已经获得／更新实体；

- 实体处于当前客户端会处理和绘制动画的可见范围。\
  服务器选择成功不等于后两者成立。也不能把“在天上加载后成功”误解释为“狐狸只有在天上才能渲染”。

y=100 是旧安装栅格位置，不是动画生效的自然要求。真正要满足的是安装与运行时实体在客户端适当范围内，并且身份及动画状态已建立。

最终召唤链先在栅格加好身份标签，末尾把狐狸传送到持枪玩家眼前约 2 格。渲染可以随后单独触发，狐狸已经堆叠也可以重建身份，不必玩家每次 tp 到天空里随机狐狸附近。

最终跟随（原文）：\
execute as @a[tag=k47p,c=1,hasitem={item=snowball,location=slot.weapon.mainhand}] at @s anchored eyes positioned ^ ^ ^2 run tp @e[type=fox,tag=k47f] \~ \~ \~ 0 0

这里“狐狸根位置在前方 2 格”与“枪械最终显示在相机局部坐标哪里”是两个参数；改变载体位置不应被当成唯一的持枪姿态调节手段。

原版狐狸几何快照声明 visible_bounds_width=3、visible_bounds_height=2.5、offset=(0,0.75,0)。这能提示剔除范围与变换后的远距离物品不一定一致，但样例边界不能直接证明用户版本每一帧如何剔除。大转头短暂消失仍应作为单独边界记录，不能用帧补偿已成功推导它也必然解决。

## 08 原版动画是可编程骨骼输出口

核心技巧不是给狐狸加载自制动画文件，而是通过 playanimation 调用已有动画，再在表达式里写入这些动画会读取的变量。跨实体复用依赖骨骼名称的交集与原版动画定义，不能只看动画名字。

最终职责：

- animation.player.sleeping / controller.animation.fox.move：持续执行 R001 几何、姿态、相机矩阵计算，同时其原生 root／head 变换也是 FMBE 链条的一部分。

- animation.player.attack.rotations / k47r：赋 x 编号并输出身体 Y 旋转。

- animation.creeper.swelling / k47s：赋 z 编号并输出 body/head 缩放。

- animation.minecart.move.v1.0 / k47u：root 平移运输；最终帧采样与补偿也集中在此表达式。

- animation.ender_dragon.neck_head_movement / k47h：赋 y 编号，固定头部的几何补偿与旋转。

- animation.warden.move / k47b：输出身体 X/Z 旋转、约束相关头部旋转变量。

- animation.player.riding.arms / k47e：最终保留的旧采样器占位，表达式 return 0；不再采样。

- animation.player.riding.arms / k47q：持续设置 v.k64=1，选择最终根位移补偿模式。

- k47t22：三种不同的原版手臂动画发一次性姿态信号。

- k47t23：C23 候选的换弹开始／取消信号。

原版 sleeping 本身还直接读取 q.body_y_rotation 和 q.sleep_rotation，且 override_previous_animation=true；不能因为集中计算了自己的变量，就宣称所有变换均已集中、所有原生查询都被冻结。它本来参与固定坐标映射，也不能看到它读朝向就认定其一定错误。

表达式中的 return 0 用于让相关安装状态持续；return 1 用于本项目的一次性赋值信号。具体能否覆盖旧动画仍取决于安装状态、控制器和引擎实现，不能抽象成“同名一定完全替换”或“新命令永远不会替换”。

命令块不再执行，不等于之前装到客户端上的持续动画已经被移除。用户把 playanimation 前加汉字使块报错，只能停止那条安装命令后续成功执行；不能据此认定旧动画立即停止。这里曾是实验解释的重要陷阱。

playanimation 的形态为：playanimation \<targets> \<animation> \<next_state> \<blend_out_time> \<stop_expression> \<controller>。本项目长引号中的赋值位于 stop_expression，利用其求值副作用更新动画要读取的变量；它不是另一个 JSON 动画定义。none、0、控制器名和 return 值都有各自作用，压缩命令时不能误删。一次 playanimation 被接受，也不证明表达式每一项都按预期参与了当帧最终骨骼输出。

## 09 几何变量与坐标约定

最终 R001 从零件编号查出：

- v.k0..k2：零件中心 p，坐标轴依次为镜头前方、上方、侧向；

- v.k3..k11：3×3 局部基底 B，按行存储；

- v.k12：两条相等轴对应的厚度参数；

- v.k13：单轴比例的平方根；

- v.k20..k28：相机变换后的 3×3 基底 M，按行存储。

默认 B：\
[0 0 1]\
[1 0 0]\
[0 1 0]\
这不是错误的单位矩阵，而是狐狸口衔物、原版动画和模型轴之间已有固定映射的一部分。不要把 B 的某一列直接当成 HTML 标准立方体同名轴，忽略引擎骨骼链里的轴置换。

每帧都先恢复默认基底、读取该零件的原始表项，然后应用当前动作，再转到世界方向。该顺序避免对上一帧已经变换过的几何继续旋转／缩放造成累计漂移。

HTML 几何定义为：\
world_local = translation(center) × Rz × Ry × Rx × scale(size) × unit_cube\
unit_cube 每轴范围 [-0.5,0.5]。\
R001 基础中心等于 HTML center+(0.66,-0.174,0.245)。该偏移是持枪基准，并非狐狸在世界中的实际位置。

Molang 的相关三角函数按角度制使用。把离线 JS 的弧度直接填入 math.sin/math.cos 会导致错误。需要区分临时 t.kN 与持久 v.kN：同一个数字后缀并不表示同一个变量。

## 10 镜头跟随的数学结构

令 θ=q.camera_rotation(0)，ψ=q.camera_rotation(1)。最终代码使用：\
F = (-sinψ cosθ, -sinθ, cosψ cosθ)\
U = (-sinψ sinθ, cosθ, cosψ sinθ)\
R = (-cosψ, 0, -sinψ)\
W = [F U R]，三列分别是前、上、侧。

对零件局部中心 p=(p0,p1,p2)：\
目标世界偏移 = F p0 + U p1 + R p2。\
对局部基底 B：\
M = W B，存入 k20..k28。

因此，枪身跟随视角的关键是“用相机基底变换每个零件的中心和方向”，不是把每只狐狸的实体朝向设置为玩家朝向。狐狸只是载体；实体朝向、镜头角度、枪械动作姿态是不同输入。

动作阶段先对整枪施加 Q：\
p' = Q(p-pivot)+pivot+offset\
B' = Q B\
再计算 M=W B'。只转中心而不转基底，零件会沿圆周走但自身方向不对；只转基底而不转中心，零件原地自转，整体也不对。

在同一时刻、同一 Q 且 Q 正交的条件下，对任意两部件中心：\
|p'\_i-p'\_j| = |p_i-p_j|。\
这是整枪刚体动作的离线检查依据。缩放是每个部件几何的原始属性，不应该因切换跑动或瞄准而被重复乘入。

## 11 平移运输从 head 移到 root 的意义

早期补偿把相机相对的大位移写入 head_position_x/y/z，再经过具有各部件不同缩放／旋转的骨骼链。理想公式当然可以抵消实体位置，但实际求值、原生骨骼叠加和缩放层级一旦有误，误差可能随部件不同而被不同地放大或旋转。

后来的 root_transport 路径把“把实体处的物品搬到相机前”交给矿车动画 root 位移；head 只保留该零件自身固定的口衔几何校正。这样把大尺度空间运输与不同部件的缩放／姿态分开，是从散架转为主要整枪抖动的重要结构变化。

[A] 这说明为何修改骨骼层级可能比单纯集中变量有效；并不证明已逆向得到所有引擎内部错误，也不保证任意安装状态下 root 运输一定成功。

最终头部：\
s = sqrt((32/7)×max(k12,10^-6))\
e = max(k13,10^-6)\
head_position = (0, (16/s)×(10/7)×e×k12, -(16/s)×(16/7)×k12)\
head_rotation = (180,0,180)

最终大位移由 q.rotation_to_camera、q.distance_from_camera 重建。设 a、b 为该查询的两个角度，d 为距离，按源码定义：\
D = (-sin(b)cos(a)d, -sin(a)d, cos(b)cos(a)d)\
T = D + Wp + (-1,-1/128,0) + wΔ

再用狐狸 body_y_rotation=β 转到所需骨骼坐标：\
rail_offset.x = 16×model_scale×(cosβ Tx+sinβ Tz)\
rail_offset.y = model_scale×(18.5+16 Ty)\
rail_offset.z = 16×model_scale×(sinβ Tx-cosβ Tz)\
hurt=0，rail_rotation.z=0。

这里的 -1、-1/128、18.5、16 属于特定原版几何和坐标换算。历史资料中原 FMBE 实现也存在 xpos-1、ypos-1/128。不能因为某条旧 tp 恰好包含 \~1 就把 -1 当成遗留误差删掉。

用户问“不是不依赖狐狸绝对坐标吗”：显示目标可以不依赖载体落点，但求出抵消载体位置的补偿仍然依赖测得的相对位置，以及该测量与最终绘制的一致性。“理想结果与载体位置无关”不等于“运行时完全不读取或不受载体状态影响”。

## 12 旋转、缩放与原版骨骼链

缩放输出：\
s1 = sqrt((32/7)×max(k12,10^-6))\
s2 = max(k13,10^-6)×s1\
creeper.swelling 同时对 body 和 head 使用 [s1,s2,s1]。两级祖先缩放相乘，因此最终比例出现平方，而不是一层的 s2/s1。再结合狐狸口衔方块的基础显示尺寸，得到 k12 和 k12×k13² 的几何维度。

原版狐狸关键骨骼链为 world→root→body→head→held_item；几何快照中 body pivot=(0,8,0)、head pivot=(0,8,-3)、held_item pivot=(-2,3.3,-13)。这些固定偏移解释了为什么不只是三行“设位置、设角度、设大小”就能拼出正确结果。

世界基底 M 的旋转解码：\
attack_body_rot_y = atan2(-k24, sqrt(k23²+k25²))\
body_x_rot =\
abs(k25)+abs(k23)>10^-7 ? atan2(k25,-k23) : atan2(-k20,-k22)\
body_z_rot =\
abs(k25)+abs(k23)>10^-7 ? atan2(-k21,k27) : 0\
head_x_rot=0，head_z_rot=0。

退化分支处理的是该欧拉角分解接近特殊方向时的数值问题。它不等于“某个世界朝向天然无法渲染”。此前正负 X／负 Z 的可见性差异已经被用户定位到狐狸根部视野条件，不能混为一谈。

几何参数的 max 下限是避免零或负缩放参与开方／除法的防护，不是修复所有错误编号的万能措施。编号错误会选错零件，即使公式没有 NaN 也会组成错误枪形。

## 13 三种不同故障必须分别命名

故障 A：未渲染／掉回狐狸嘴边。\
表现：隐形狐狸叼着散落的小方块；初始化没有建立预期骨骼运输。\
可能涉及：实体未在客户端有效加载／可见范围、安装链未完整执行、某动画输出缺失、旧状态覆盖、冷启动变量、公式出错。\
不能仅用“位置插值”解释所有 A。

故障 B：相对散架重组。\
表现：不同零件彼此分开、自转或错位，随后重新拼合。\
数学约束：若所有部件都只有完全相同的平移残差 e(t)，那么显示位置 P_i=T_i+e，任意 P_i-P_j=T_i-T_j，整枪只会一起偏移，不能散架。\
因此 B 至少需要某种非共同误差：不同实体更新／呈现位置、不同骨骼变换、不同写入者、不同选择时刻、不同缩放放大，或者上述机制组合。\
“有客户端插值”本身不是 B 的完整证明。

故障 C：整枪弹簧式抖动／边缘快速重影。\
表现：枪形基本完整，但随跟随 tp 周期往返；枪身边缘闪动，移动／转头时显著，停下后较稳。\
这一阶段才与“查询采用的位置与绘制插值位置存在帧内差值”的模型高度相符，最终 α 补偿取得明显改善。

剔除／短暂消失另列为故障 D。它可能和大幅转头、载体位置有关，不能把 C 解决后自动标成 D 也解决。用户所说“影子”在此是边缘重影的描述，不应未经检查就诊断为光照阴影贴图问题。

## 14 最终帧内补偿与符号选择

[D] q.frame_alpha 返回当前渲染帧在 AI tick 之间的进度，范围 0..1。它不是服务器命令计时器，也不直接返回实体速度。

解释最终公式的简化模型：\
Pprev = 前一个离散位置；\
Pcur = 当前离散位置；\
Δ = Pcur-Pprev；\
Pdraw = (1-α)Pprev+αPcur。

若补偿查询使用 Pcur，而实体画面根位置为 Pdraw：\
Pdraw-Pcur = -(1-α)Δ。\
因此在骨骼搬运上再加 +(1-α)Δ，可以在这个模型中抵消残差。对应 M1。

若查询使用 Pprev：\
Pdraw-Pprev = αΔ。\
需要补 -αΔ。对应 M2。

最终实际源码：\
w = (v.k64==1) ? (1-q.frame_alpha)\
: (v.k64==2) ? (0-q.frame_alpha)\
: 0\
T += w×(v.k70,v.k71,v.k72)\
v.k64 由 k47q 持续设置为 1。

[U/C] 用户反馈先有一个尝试无改善且略重，后来一个尝试“神了，和静态效果几乎一致”；最终世界保存的是 M1。可据此保留 M1 为本环境有效基线。不能仅凭这件事把整个引擎位置采样顺序定性为已完全证实，因为 Δ 的采样路径、动画叠加和相机查询本身也参与结果。

关键实施改动不只是写出 (1-α)Δ：

- 位置采样和 rail_offset 输出放入同一条 minecart 表达式；

- 对历史变量进行 ?? 初始化；

- 旧 k47e 外部采样器停止写入；

- 保留已验证的 root 运输公式和固定几何；

- 在冷启动与实际安装链中验证，而不是只在热状态探针上验证。

## 15 最终采样器状态机、优点和限制

最终 root 表达式使用：

- v.k70..72：最近一次接受的 Δx/Δy/Δz；

- v.k73：上一渲染求值看到的 frame_alpha；

- v.k74：预热计数，上限 3；

- v.k75..77：上次边界采样的 q.position(0/1/2)；

- v.k64：模式。

初始化：\
alpha_old ?? 当前 alpha；\
warmup ?? 0；\
pos_old ?? 当前实体位置；\
delta ?? 0。

当 当前 alpha < 上次 alpha 时，视为观察到一次进度回绕：

1. warmup 小于 3 则加一；

2. delta=当前位置-pos_old；

3. 更新 pos_old；

4. 若 warmup<3，或 |Δx|+|Δy|+|Δz|>3，则把 delta 清零；

5. 每次求值都更新 alpha_old。

前两次观察到的回绕被抑制，第 3 次可以使用正常 Δ。阈值使用 L1 和，不是欧氏距离。大于 3 格的跳变被主动排除，因此该代码并非承诺修复任意跨度传送。

优点：[A] 同一表达式内先采样后消费，减少“一个动画更新 Δ、另一个动画在未确定时刻读取”的跨控制器依赖；初始化避免冷状态直接消费不存在的历史值；预热避免第一次历史样本不可靠。

限制：

- alpha 回绕不是无损 tick 时钟。低帧率可能跨过一个或多个 tick 后 alpha 仍增大，漏掉边界；也可能一次位置差覆盖多个 tick。

- 若状态暂停、实体不求值、离开视野或重载，历史样本可能过时。

- 不同狐狸仍各自求值；把表达式合并不等于创建了全局共享时钟。

- q.position 的查询时刻与距离／角度查询的时刻是否完全相同，没有足够接口保证。

- 大跳、快速转头、低帧率等边界需要另测。

- 最终 k47q 每帧写模式 1；想用聊天临时改 v.k64 必须考虑这个持续写入者，否则可能下一帧又被改回。

维护原则：如果目标只是改跑动位置或换弹，不要顺手改这个稳定采样器。若确需优化，保存逐字原文，针对明确复现条件做一项变化。

| 尝试 | 观察／结果 | 可以得出的结论 |
| - | - | - |

## 17 冻结与探针为何曾误导调试

冻结实验必须先证明干预实际生效：

- 原版是否能复现？

- 覆盖后、不移动实体时是否仍保持完整？

- 被冻结的量是否真的不再响应相应输入？

- 是否有旧循环或另一个动画写回？

- 狐狸是否仍在有效视野内？

- 恢复原文后现象是否回来？

头部位置冻结只停止某条补偿路径。角度仍更新是可能的预期；整枪跟着实体根移动也是预期。不要把整体位移、正常透视变化和相对散架混在一个“有反应／没反应”里。

早期探针一：在 fox.sit 上执行测试表达式后 return 1，看到“只闪一下”。\
问题：正常停止和错误提前结束可能产生相似外观；不能据此证明整个表达式执行完成。该探针的正面结论应作废。

后期探针二：在 parrot.moving 上执行测试后写 wing_flap=20，return 0，出现持续位移作为正向信号。比“只闪一下”更有区分力，但仍有边界：

- 探针 G 直接写生产 rail_offset，再由另一个动画改变 body，已经参与被测系统，不能当完全无扰动测量。

- H 使用 20+0×k70+0×k71+0×k72，只能说明某种表达式路径没有阻止最终现象；不能证明这些变量数值正确、同步或非零。

- 读未定义变量的 I/J 热测试成功，不能证明每种冷启动顺序都安全。

- 新建另一个控制器 k47w 后处于“成形与散架中间”，不能直接证明旧 k47u 已被清干净。

- 命令块停止发令不等于安装的客户端动画停止。

有效的最小增量策略曾包括：原始根输出→常量小位移→字面 0→临时变量 0→持久变量初始化→模式分支→frame_alpha→已知 Δ→真实采样。每一步应有一个明确可观察差异和独立回退。不能把“数学上加零”等同于引擎生命周期完全等价。

## 18 对物理挤压和共享玩家数据的回答

物理挤压假设为何合理：75 个原生实体在同一点，碰撞、下落、AI 旋转可能让各自根状态不同；如果补偿使用的位置与实际绘制状态不一致，就可能显现误差。理论位置抵消不是让实体物理状态消失。

物理挤压为何没有成为最终根因结论：[U] 用户把狐狸分散后仍观察到重组，因此至少在该实验条件下，近距离堆叠不是故障出现的必要条件，不能继续把“全是挤压”当已证实结论。不同落点、不同更新时间、原生根变换和旧动画状态仍需分别看待。

“每只狐狸都读玩家数据吗”需要精确回答：

- q.camera_rotation 是当前渲染观察者的相机信息，不是从服务器玩家标签中直接拷贝一个共享结构。

- q.position、q.body_y_rotation 等是当前动画实体的查询。

- 每只狐狸的 v.\* 是各自的状态，不存在只因变量同名就自动跨实体共享。

- 在一个狐狸上计算 v.a，再让其他狐狸读取同名 v.a，并不会建立全局广播。

- 要真正引入共享采样，需要明确可访问的传输机制；纯命令＋原版动画环境不能假设拥有资源包脚本里的共享数据 API。

- 本项目没有通过新增“主狐狸”或辅助实体解决。有效办法是减少跨动画依赖、正确选择骨骼层级，并补偿本实体的运动残差。

- 把相机矩阵集中到同一表达式能减少同实体内部重复与顺序依赖，但不能据此宣称 75 只狐狸在同一 CPU 时刻求值。

若以后研究不同实体是否不同步，应测量“同一可见帧内的相对误差”，而不是仅凭实体数量或看到重组就命名为网络不同步。

## 19 常态 跑动 机瞄的单驱动状态机

最终状态变量：\
v.k90：目标模式，0 常态、1 跑动、2 机瞄。\
v.k91：当前跑动权重。\
v.k92：当前机瞄权重。\
v.k93：过渡进度。\
v.k94/v.k95：本轮切换开始时的跑动／机瞄权重。\
v.k96：上一次目标模式。\
v.k97：循环动作时间。

当 k90 != k96：\
记录当前权重为起点，k93=0，k96=k90。\
随后：\
dt=max(0,q.delta_time)\
k93=min(1,k93+dt/0.22)\
h=k93²×(3-2k93)\
k91=start_run+((k90==1)-start_run)×h\
k92=start_aim+((k90==2)-start_aim)×h

这就是动作平滑过渡的直接实现：客户端每帧更新两个权重，再用权重重算几何。不是依靠服务器每帧重发姿态，也不是依靠 playanimation 的 blend_out_time；这里命令参数为 0，缓动是手写的。

0.22 秒为名义过渡时间。中途切换会从当前权重继续，不必先瞬移回常态；位置连续，但重新开始 smoothstep 可能改变瞬时速度，不应声称所有中途切换都具有严格一阶连续性。

时间：\
k97=mod(k97+dt,5)\
phase=k97×792（度）\
sin(phase) 为 2.2 Hz，cos(2phase) 为 4.4 Hz。\
5 秒恰好包含 11 个主周期，模回绕在理想公式下不造成相位断点。

每帧先读原始零件表，再应用当前权重。不会把上次跑动后的坐标再次当成原始坐标旋转，这是保持整枪几何和连续切换的关键。

## 20 跑动与瞄准的最终参数

整枪枢轴 pivot=(0.66,-0.174,0.245)。\
跑动三个旋转输入分别由以下值进入源码中的 Q 矩阵：\
75×run；\
(-6+0.45×cos(2phase))×run；\
(-12+0.8×sin(phase))×run。\
轴向／乘法顺序以附录矩阵代码为准，不能只拿三个数字套进任意软件的欧拉角顺序。

变换后中心附加：\
forward: +0.66 -0.21×run +0.03×aim\
up: -0.174 -0.116×run +0.025×aim +0.006×(cos(2phase)-1)×run\
side: +0.245 -0.125×run -0.245×aim +0.010×sin(phase)×run

用户先要求更垂直、枪口更偏向视角左下，再确认横摆 75°合适。之后两次要求跑动更靠近，最终基线用 -0.21 的前向位移把枢轴从 0.66 拉近到 0.45。不要拿早期“离玩家太远”的版本代替当前成功版本。

跑动看起来变小不一定是模型真的被缩小：整枪旋转后的投影长度和深度变化会改变屏幕占比。最终跑动公式不改变 k12/k13，主要通过位置和角度调整观感。

机瞄把侧偏从 0.245 收到接近中心，前向加 0.03、上移 0.025。当前代码是枪械位置对准，不包含摄像机 FOV 变焦。机瞄是否像真实机械瞄具一样几何共线，应以模型瞄具位置和实际画面验证，不凭名称自动保证。

## 21 为什么旧姿态会叠加，以及 C22 的修复

[U] 用户发现常态后点机瞄，出现两者混合；跑动、机瞄无法互相覆盖；甚至不退出世界而重召狐狸，仍可出现叠加结果。

[C/A] 旧 C21 设计让不同姿态的长表达式各自持续写目标值并持续插值。同一变量有多个活跃写入者时，即使每个单独公式都正确，合起来也会争抢目标或重复重置过渡。离线诊断曾在“两个驱动均继续运行”的假设下得到中间权重约 0.504；这是机制演示，不是测得用户引擎内部真实权重。

C22 改成：

- 只有 R001 一个持续姿态驱动；

- 新变量空间 v.k90..97，减少与旧 v.k80..87 状态混淆；

- 三个很短的一次性命令只写 k90，随后 return 1；

- 三种不同原版手臂动画作为模式信号；

- 保持 root 运输／补偿独立。

当前三条触发信号：\
常态：animation.player.riding.arms，v.k90=0;return 1;\
跑动：animation.player.riding.arms.zombie，v.k90=1;return 1;\
机瞄：animation.player.holding.zombie，v.k90=2;return 1;\
共同控制器 k47t22。

用户想要的是带 testb 执行一次跑动、带 testc 执行一次机瞄，以及一个还原常态的触发器。最终消费标签后删除标签，不应再塞回三个各自常驻的长动画控制器。

单一写入者不是要求整个枪械只有一个动画：root、缩放、旋转等仍有各自输出。它要求“同一个状态量由明确的一处维护”，尤其避免多个完整姿态计算器竞争。

[H/X] 旧命令究竟因为哪种客户端缓存／控制器覆盖细节继续存活，未被唯一确定。重召实体仍混合的观察不能单独证明缓存一定是全局的。工程修复可以确定有效，不必伪造一个更精确的内部机制结论。

## 23 潜行 移动 跳跃检测的经验

用户拒绝为了简单动作检测增加辅助实体，倾向利用当前版本 execute/anchored 的经验性行为。最终世界确实没有额外的专用移动检测实体。

移动检测原文保存在附录。关键结构：\
as 玩家 at 玩家 anchored feet\
unless entity @s[r=0.03]\
再恢复 as @s at @s，\
排除水／岩浆，\
用 y=\~1.82 与 \~1.80、dy=0 的选择器条件限制站姿状态，\
添加 移动 标签。

这不是官方的“正在疾跑”布尔查询，而是用户在该版本验证可用的移动／状态启发式。不能保证能区分普通走路、疾跑、被推动、移动平台或所有飞行状态。anchored 延时是用户的经验线索，不应宣称官方合同保证其每个版本固定延迟一个 tick。

潜行检测：\
execute as @a[tag=k47p] at @s unless entity @s[y=\~1.5,dy=0] if entity @s[y=\~0.7,dy=0] run tag @s add 潜行

跳跃检测：\
execute as @a[tag=k47p] at @s if block \~\~-0.1\~ air 0 run tag @s add 跳跃

这些是特定碰撞箱／方块条件的代理检测，不是直接读按键。台阶、半砖、游泳、爬行、飞行等边界不能无测试保证。

用户最初提供的移动命令还带 unless block \~ \~-1 \~ air 0；跳跃会导致移动与不移动反复变化。最终世界版已没有这个条件，并通过 移动2、潜行2、回调 等标签做进入／退出状态的边沿处理。不要拿最初命令当最终完整判定。

当前世界的 跳跃2 标签有移除逻辑，但本提取中未发现给它赋值的对应命令。不要替源码补想象中的完整跳跃锁存器；用户可能在别处测试过，也可能是保留痕迹。本文记录真实快照，不擅自“整理掉”可疑但现有的逻辑。

原则：检测输出一次性请求，视觉侧平滑插值。避免检测每帧抖动直接变成多个长动画来回覆盖。若新增动作，只在出现明确误判时改检测，不要为了动画参数调整同时重构输入逻辑。

## 24 开火的 c=2 分支复用

用户要求雪球触发；目标排除狐狸和玩家，不只攻击僵尸；不要单人项目工业化。最终还排除了射线载体雪球本身。

开火流程：

1. 把检测到的雪球传送到持枪玩家眼睛位置。

2. 连续 9 个 as @e[type=fox,tag=k47f,c=2] 形成分支。

3. 若每层都选到 2 只狐狸，末端运行次数为 2^9=512。

4. 每个末端进入一个新的 execute：重新 as 雪球 at 雪球，使用玩家朝向。

5. 在当前位置做目标实体检测；未命中则沿局部前方 tp 0.125。

6. 所有末端完成后，在最终位置选实体施加 11 projectile 伤害、生成命中粒子、播放开火反馈。

7. 删除雪球。

最大名义前进量：512×0.125=64 格。它是命令推进距离，不是经过全部边界验证的精确弹道射程。

“run execute ... at @s” 重新建立位置上下文非常重要：前一个末端改变雪球位置后，下一个末端需要重新读取新位置，才能逐步推进。同一层旧上下文如果一直保持最初坐标，可能只是重复传到同一个点。不能在优化时把这个看似多余的 execute 随手折叠掉。

c=2 复用的是命令执行分支，不会复制狐狸，也不是无限免费循环。若不足 2 个可选狐狸，次数不再是 512；若有多个雪球，处理量会乘上雪球数量。当前单人方案接受这一范围，不需擅自引入多用户所有权框架。

射线检测使用 positioned \~-0.5 \~-0.5 \~-0.5 与 dx=0,dy=0,dz=0 的体积选择，再把执行原点移回。不能把这个选择体积称为数学上的无宽度射线。tp 末尾 true 用于目的地方块碰撞检查，也不是任意形状连续碰撞检测引擎。

一旦命中，后续分支在相同位置重复检测而不继续前进，所以最终 damage 施加于命中端点。命中不是每个分支都扣血；当前命令把伤害放在分支步进之后。

大数圆规曾被提出作为候选技术，但最终成品代码走的是 c=2 分支步进，不能把未采用的候选写成最终实现。

## 26 音效 隐藏与狐狸保护

用户早期觉得声音小，明确要求僵尸破门和凋零摧毁方块一类更明显的原版音效。最终世界保存的枪声是 mob.zombie.woodbreak；没有足够本轮源码依据恢复当时所有试听命令，因此不编造“最终同时用了凋零声”。

停止音效列表（当前世界实际配置）：\

mob.fox.ambient、mob.fox.aggro、mob.fox.bite、mob.fox.death、mob.fox.eat、mob.fox.hurt、mob.fox.screech、mob.fox.sleep、mob.fox.sniff、mob.fox.spit；\

invisibility infinite 0 true；\

这是用户要求的简洁方案，也是当前源码。不能把它描述成禁用 AI、无碰撞、无重力或任何情况下绝对无敌。原始 minecraft 只更换行为组件，仍涉及小睡、找遮蔽等行为，不等于冻结狐狸；最终每 tick 跟随另行约束位置。

当前世界另有全局掉落物／经验球清理和一个 kill @e 按钮。它们不是 FMBE 成立的必要条件，迁移时应与模型／开火核心分开理解，不能以“完整安装”为由默认清空其他世界实体。

- 整枪抬起并侧倾；

## 30 HTML 预览能做什么 不能做什么

适合在 HTML 里确认：

- 75 部件的比例、材质、命名和组别；

- 跑动横摆 75°、抬枪、侧倾、靠近玩家的视觉方向；

不能通过 HTML 证明：

- 原版动画在狐狸上能否正确安装；

- 服务器 tp 与客户端帧插值是否一致；

- 相机查询、骨骼求值与渲染剔除顺序；

- 返回表达式覆盖旧控制器的实际行为；

- 网易版的命令长度、命名过滤与生命周期差异；

- 手机上的真实 FPS、命令链负荷和延迟；

- 持久标签与客户端状态的重载行为。

HTML 模型只保存视觉用方块几何，单位是游戏格，不是现实枪械制造数据。接手工作应继续以游戏视觉与玩法命令为范围。

从预览到命令的正确迁移不是手工猜每个零件：使用同一份模型数据、明确变换顺序、映射到最终狐狸 id，并离线对照中心／大小／组别。此次 75 项对应关系已经验证，可直接沿用附录。

## 32 命令包交付和实验管理的经验

一次有效交付应包含：

- 当前基线来源和明确修改对象；

- 完整可复制命令，不省略长表达式的中间部分；

- 脉冲／循环／连锁、是否有条件、是否需要红石、延迟、连接顺序；

- 这条命令是替换原块、临时覆盖，还是独立按钮；

- 预期的可观察差异；

- 与当前基线逐字一致的回退；

- 实际验证范围。

本项目明确出现过的交付事故：

1. JSON 格式版本写成 r1，导入直接失败。

2. 让用户“打开 JSON 自己复制”而不给需要的短命令，增加操作成本。

3. 没有确认冻结有效就继续解释冻结结果。

4. 替换一条命令与再安装五条的目标没有讲清，用户不知道改哪个块。

5. 长表达式热探针成功，被当作完整安装成功。

6. 把此前未成功的 tp 尾参数、集中计算或距离建议重复包装成新修复。

7. 把尚未进行的研究结论说成唯一根因。

8. 未保存当前成功版本，导致后续 AI 只能拿早期故障包继续猜。

9. 用“第 12 号”而不说明是渲染链编号还是整个世界编号，容易改错块。

10. 默认旧实验控制器已消失，导致新旧写入者混杂。

命令复制助手文件：

- mccmd 必须数字 1；

- sections 分区，items 列命令；

- cmd 保存真实命令字符串；

- block.type、conditional、redstone、delay 类型正确；

- 布尔是 JSON boolean，delay 为整数；

- 不把独立测试／恢复按钮自动串成链；

- 召唤与渲染放同一个文件不同区，仍可分别运行；

- 不给恢复文件起与旧 rollback 混淆的名字。

包结构检查不能保证游戏语义。应分别记录“可解析”“符合复制助手结构”“原文一致”“数学检查”“引擎接受”“用户实测成功”，不要合并成一个含糊的“验证通过”。

## 34 故障分诊与接手优先级

若重新出现“只看到狐狸叼方块”：\
先核对实体是否在客户端可见范围、k47p/初始化 条件是否成立、渲染链是否完整执行、04-13 root 是否仍是有效版本、是否有旧安装循环。不要第一步就改数学补偿。

若零件编号混乱但每个零件稳定：\
查 x/z/y 标签是否唯一、是否遗漏标签、k44 计算是否与模型映射一致、材质选择区域是否被改。不要先调 frame_alpha。

若整体形状正确但随 tp 弹簧式抖：\
查 M1 是否真的保持、k47e 是否仍有旧写入、04-13 采样与输出是否合并、跟随是否每 tick、是否改了 large-jump 阈值。再测低帧率／剔除边界。

若状态混合：\
查是否存在多个长姿态驱动、旧测试块是否继续安装、k90 谁在写、k47t22 是否是一帧赋值、是否误用持续 return 0 信号。不必先重建 75 零件几何。

若动画平滑但方向不对：\
先核对矩阵乘法顺序、角度单位、枢轴、中心与基底是否同步变换。不能只靠给某个角度加负号反复试。

若大转头短暂消失：\
将其列为可见性／更新边界复现，记录实体根位置和画面。不要把它重新命名为已解决的抖动，也不要未经验证宣称纯命令必然无解。

若要继续换弹：\
从稳定世界 R001 与 C23 对照开始；先做纯视觉验证，不改 root，不追加新的全枪长驱动；成功后才按用户要求接 ammo 和射击状态。现阶段最有价值的扩展是完成已有候选，而不是重新研究已解决的集中计算、0 0 删除或挤压假设。

## 35 可复用的技术结论

1. 位置无关的理想显示结果，仍依赖正确测量并抵消载体位置。

2. 同一公共平移误差只能移动整枪；要解释散架，必须找非共同误差。

3. 不同骨骼层级的职责分离能改变误差性质：大尺度运输放 root，零件几何留在局部链。

4. 服务器 tick、动画求值、绘制插值是三个不同阶段。

5. q.frame_alpha 给出插值进度，但不能单独提供无损 tick 边界、实体速度或全局同步。

6. 同一表达式内的先写后读比跨控制器的隐含更新顺序更可控；并不等于所有实体全局同步。

7. 每个状态量应有明确唯一持续写入者；切换命令发送目标，持续驱动负责过渡。

8. 中断动作应从当前权重开始，原始模型每帧重建，避免累计变换。

9. 狐狸实体身份应与世界位置解耦，标签使堆叠后重初始化成为可能。

10. 载体根进入视野是运行条件之一，骨骼远距离搬运不会自动扩展所有剔除条件。

11. 一次安装后持续求值与循环重复安装是不同机制。

12. 禁用命令块不自动卸载已经安装的动画。

13. 热状态探针成功不证明冷安装成功；正向输出信号比“只闪一下”可靠，但仍需避免污染被测变量。

14. 单人方案可以用现有实体分支驱动有限次步进，不必为每个功能新增辅助实体。

15. 分支倍增能压缩命令块数量，不能消除运行成本。

16. 离线模型与游戏几何应来自同一数据集，并保存明确 id 映射。

17. 资源格式、导入格式、数学正确、引擎语义、实机效果要分别验证。

18. 玩家实测胜过“看源码应该能行”，但一次实测也不代表所有版本和边界。

19. 保留负面结果是为了减少重复失败，不是把候选机制永久判死。

20. 一份可继续工作的交接必须保存有效源码、回退和实测范围；只留下猜测性结论会让后续 AI 重走原路。
